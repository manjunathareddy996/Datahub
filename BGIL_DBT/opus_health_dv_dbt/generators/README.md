## Run order

```
python run_hcon_build.py --fresh     # deletes models/ and build_artifacts/, then:
   1. hcon_writeguard.py             prove the write guard REFUSES and the digest tool reproduces a known answer, before anything is written
   2. hcon_names.py                  probe every regex and every naming rule; a pattern that cannot match reports a zero indistinguishable from a clean result
   3. hcon_keyrules.py               assert the profile and the map field-by-field, re-measure the profile's load-bearing claims, and prove the walk-operator zero
   4. build_hcon_spec.py             the ONE place the map is interpreted; everything after reads the spec
   5. gen_hcon_staging.py            layer-1 casts; the stage layer refs these
   6. gen_hcon_hopviews.py           walk-only casts: PROVE the zero
   7. gen_hcon_resolvers.py          ancestor resolvers: PROVE the zero, twice
   8. gen_hcon_stage.py              one wide stage per view, carrying the business-key columns
   9. gen_hcon_unpivot.py            column-as-instance fan-out; reads the stage layer
  10. gen_hcon_vault.py              hub feeds, hubs, links, satellites -- reads the stage layer
  11. gen_hcon_augmented.py          the unratified track; imports the vault renderer so both tracks share ONE satellite renderer
  12. gen_hcon_rejectlog.py          the complement of every feed's WHERE clause
  13. gen_hcon_assertions.py         LOAD-TIME assertions: the registry hazard and the intra-run arbitrariness are DATA questions and cannot be settled statically. Emitted and UNRUN.
  14. check_hcon_reachability.py     every <X>_HK referenced is produced locally or by a ref()ed model -- fixpoint over the ref graph
  15. check_hcon_payload_naming.py   the payload-naming half that check_vault_alignment cannot reach in this layout
  16. emit_hcon_status.py            BUILD_STATUS.json -- every count lives here and nowhere else
  17. gen_hcon_readme.py             generators/README.md, generated FROM BUILD_STATUS.json; it must exist before any gate or proof reads it
  18. run_hcon_gates.py              every gate as a subprocess, exit codes read UNPIPED, population recorded, a PASS on an empty population downgraded to NOT RUN
  19. prove_hcon_checks.py           prove every check by INJECTION against a copy of the real corpus: it must FIRE on the defect and stay SILENT on the clean corpus
  20. emit_hcon_stage1_report.py     the stage-1 completion report; needs the gate verdicts and the proof results, and every builder decision appears as a decision_taken finding so the handback cannot omit one
```

`--fresh` exists because **reproducibility is proved by deletion**. A build that only works
on a second run is not reproducible; it is inheriting state.

## What is different about this LOB

1. **It consolidates TWO closed builds into a third.** Both originals are READ-ONLY and
   are re-digested at every stage boundary; `hcon_writeguard.py` records every write to a
   cross-process manifest and refuses any path outside this project.
2. **The legacy half of the map carries no resolved_key at all**, so legacy hub key
   expressions are recovered from `health_dv_dbt`'s EMITTED SQL (builder decision BD2).
   That is the only input in this build that is not the bundle, and it cannot be validated
   against the bundle. See `BUILD_STATUS.json` &rarr; `legacy_key_archaeology`.
3. **Two independent writers of one attribute.** No standard layer expresses that, so the
   profile declares a bespoke `dual_feed_satellite_loader`: one row per hub key, one
   hashdiff over the union, and a DECLARED SOURCE PRECEDENCE where both runs write one
   attribute -- applied in the SQL, not only described in the header.
4. **Unifying the hash form does not unify the registries.** Six of the fourteen shared hubs share ZERO business-key columns between the runs; every shared hub header says so, and `reports/hub_registries.json` enumerates every registry per hub per run.
5. **Five carried-forward reconciliation caveats, not one** -- reproduced VERBATIM into the
   model headers. The sharpest is `lnk_party_role`, whose one-leg link hash key is
   byte-equal to `HUB_PARTY_HK` with the role token absent from the key entirely. That is a
   KNOWN DEFECT CLASS carried over, not a surprise found here.

## Where to overrule a decision

Each is ONE LINE to overrule. The cost of overruling is stated with it.

### BD1-hashdiff-name

- **Decision**: Hashdiff column is <SAT>_HASHDIFF, not a bare HASHDIFF.
- **Why** (counts in this line are taken from the artefact it names): The two originals disagree and s7 cannot decide between two equally-entitled siblings: legacy writes a bare HASHDIFF and never a suffixed one, v2 the exact reverse -- counts taken from build_profile.json sibling.hashdiff_evidence. A bare name collides the moment ONE model computes hashdiffs for more than one satellite, which is what a multi-feed consolidated stage does. s12 already records the bare form as the OPUS spelling implicated in the shared-vault divergence debt.
- **What it costs** (counts in this line are taken from the artefact it names): The estate gains a third project using the suffixed form, so a future shared loader spanning this project and legacy must translate one name. Nothing is loaded, so the change costs nothing TODAY; it costs a translation LATER.
- **Overrule with**: `hcon_names.hashdiff() -> return 'HASHDIFF'`
- **Profile status**: profile records RECOMMENDED_NOT_RATIFIED; ratified by the coordinator this run and recorded here because a decision taken in a message and not written down is a decision nobody can overrule.

### BD2-legacy-key-archaeology

- **Decision**: Legacy hub key expressions are recovered from health_dv_dbt's EMITTED SQL (read-only), because the legacy half of the map carries zero resolved_key.
- **Why** (counts in this line are taken from the artefact it names): Open item R4-builder, proposed_default: 'the build is the authority, not the map'. Without this, EVERY row of the legacy half has no hub key and every shared loader loses its legacy feed -- which would silently convert a consolidation into a v2-only build. Rows per run are taken from build_profile.json map_shape.by_source_run and the loader partition from build_profile.json layer_plan_one_loader.
- **What it costs** (counts in this line are taken from the artefact it names): The recovered expression is what legacy's generator EMITTED, not what any map declares, so it cannot be validated against the bundle. The legacy HASH VALUES are NOT reproduced (legacy hashes inside automate_dv macros whose algorithm is INFERRED_NOT_DOCUMENTED); only the BUSINESS KEY EXPRESSION is carried over, re-hashed in the canonical explicit form. Legacy's loaded keys and this project's keys are therefore NOT comparable, which is harmless only because this is a greenfield third project.
- **Overrule with**: `hcon_keyrules.LEGACY_ARCHAEOLOGY_ENABLED = False  (legacy feeds then go to UNRESOLVED and every shared loader becomes v2-single-feed)`

### BD3-no-datatype-catalogue

- **Decision**: Layer-1 casts every source column to varchar.
- **Why** (counts in this line are taken from the artefact it names): The pinned bundle contains NO datatype catalogue -- ten files, none a schema. v2's staging carries cast(... as date)/(... as number) because v2's bundle had one. Inventing a type from a column name is a fabricated datum.
- **What it costs** (counts in this line are taken from the artefact it names): Every staged column is a string, so downstream date and numeric semantics are lost at layer 1 and any arithmetic must cast again. Hashing is unaffected (every hash operand is cast to varchar anyway).
- **Overrule with**: `gen_hcon_staging.TYPE_FOR_COLUMN -- supply a catalogue and return a type`

### BD4-model-layout

- **Decision**: Models are laid out as v2 does -- models/vault/{hubs,hub_feeds,links,satellites,refs}, models/augmented, models/{staging,stage,unpivot,reject_log} -- NOT under models/automate_dv/.
- **Why** (counts in this line are taken from the artefact it names): This project declares NO packages and invokes no automate_dv macro (build directive 6). A directory named automate_dv would assert a dependency that does not exist.
- **What it costs** (counts in this line are taken from the artefact it names): STATED PLAINLY: vault_tools/check_vault_alignment.py globs models/automate_dv/*/satellites/*.sql and therefore reaches ZERO files in this layout. That gate's satellite comparison is VACUOUS here and is reported as NOT RUN, never as PASS. check_hcon_payload_naming.py was written to cover the payload-naming half against BOTH originals. Choosing the automate_dv path instead would re-enable the gate at the price of a directory name that lies.
- **Overrule with**: `gen_hcon_vault.VAULT_DIR = 'automate_dv/standard'`

### BD5-source-per-run

- **Decision**: Each run gets its own dbt source name: source('opus_health_legacy_v4', T) and source('opus_health_v2', T).
- **Why** (counts in this line are taken from the artefact it names): The two runs share NO table name at all -- per-run table counts and their zero overlap are taken from build_profile.json map_shape -- but they are two different landing areas. One source name would assert they land together.
- **What it costs** (counts in this line are taken from the artefact it names): Two source blocks to configure before this project can run. dbt is out of scope here, so nothing resolves them in this build.
- **Overrule with**: `gen_hcon_staging.SOURCE_NAME_FOR_RUN -- return one constant`

### BD6-r8-precedence-order

- **Decision**: Where both runs write one attribute, the declared precedence is V2 FIRST, then legacy: coalesce(v2_value, legacy_value).
- **Why** (counts in this line are taken from the artefact it names): v2 is the closed, settled half (profile legacy_half_status.v2_half_token = SETTLED, no Stage-9 blockers) while EVERY pre-stage-6.5 blocker and EVERY target_validity and handoff_outcome_contract finding came from the legacy half, as recorded in build_profile.json open_items. Neither run is declared authoritative ANYWHERE in the bundle, so this is a builder call and not a reading of the map.
- **What it costs** (counts in this line are taken from the artefact it names): WHERE LEGACY IS RIGHT AND V2 IS WRONG, THIS PICKS THE WRONG VALUE. The size of the exposure is taken from BUILD_STATUS.json r8 and build_profile.json r8_source_precedence. It is a VALUE choice, never a key change and never RECORD_SOURCE in a key, so it cannot alter grain and is reversible by reload.
- **Overrule with**: `hcon_keyrules.R8_PRECEDENCE = ('opus_health_legacy_v4', 'opus_health_v2')`

### BD7-refuse-not-coin

- **Decision**: A child-key leg that is NAMED but whose value is absent or of the wrong kind is REFUSED, and the satellite is built WITHOUT that leg, with the refusal in its header and in the unresolved-grain register.
- **Why** (counts in this line are taken from the artefact it names): Build directive 3, and s5.7: the map is not corrected here. The THREE legacy sub-populations -- nothing-at-all, leg-named-but-no-value, and leg-named-with-a-value-of-the-wrong-kind -- are counted in BUILD_STATUS.json and in reports/declared_unresolved_grain_hcon.json. None of the three yields a discriminator without inventing one.
- **What it costs** (counts in this line are taken from the artefact it names): Those satellites LOSE GRAIN: rows that differ only in the refused leg collapse onto one hash key. The collapse is DECLARED and countable rather than hidden, which is the only property available here -- the alternative is a fabricated discriminator that no gate can see.
- **Overrule with**: `hcon_keyrules.REFUSE_UNRESOLVED_LEGS = False (and then every collapsed row is a silent data loss)`

### BD8-ordinal-legs-are-not-hub-grade

- **Decision**: A renumbering-ordinal leg is built when the map supplies its value, and its instability is stated in the satellite header; it is never synthesised.
- **Why** (counts in this line are taken from the artefact it names): The unstable legs are named in build_profile.json renumbering_ordinals: Contact Priority Order, Coverage Sequence, Role Sequence, Active Sequence Number. Each changes when a sibling row is added or removed, so none is hub-grade -- a renumbering ordinal breaks a child key exactly as it breaks a hub key.
- **What it costs** (counts in this line are taken from the artefact it names): A source renumbering rewrites history on the affected satellites. Declared in the header so the instability is visible before load, not after.
- **Overrule with**: `hcon_keyrules.ORDINAL_LEGS_ALLOWED = False (those legs then refuse)`

### BD6b-delta3-ranked-last

- **Decision**: The third run, opus_health_delta3, is ranked LAST in the declared precedence: coalesce(v2_value, legacy_value, delta3_value).
- **Why** (counts in this line are taken from the artefact it names): MEASURED, not preferred. Delta 3 co-writes 79 of the 594 (satellite, attribute) pairs in the merged map -- 34 with legacy alone, 33 with both, 12 with v2 alone -- so the rank FIRES and is a real value choice. BD6 ranked v2 above legacy because v2 is the SETTLED half, NOT because it is newer; delta 3's settledness is established NOWHERE in its bundle, so there is no basis on BD6's own stated principle to rank it above either existing run. Ranking it first would change the chosen value on all 79 pairs the 115 build already emits, including Party Full Name, Date Of Birth and Identification Number -- a change this consolidation was instructed not to introduce.
- **What it costs** (counts in this line are taken from the artefact it names): WHERE DELTA 3 IS RIGHT AND THE EXISTING WINNER IS WRONG, THIS PICKS THE WRONG VALUE, on those 79 pairs. It is a VALUE choice, never a key change and never RECORD_SOURCE in a key, so it cannot alter grain and is reversible by reload. Delta 3's OWN 40 pairs, which no other run writes, are unaffected by the rank.
- **Overrule with**: `hcon_keyrules.R8_PRECEDENCE -- move 'opus_health_delta3' earlier in the tuple (first = delta 3 wins every shared attribute)`
